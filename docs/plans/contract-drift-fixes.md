# Plan: Contract drift fixes

## Status

**Proposed — 2026-08-18.** Derived from a full-repo duplication and leaky-abstraction
audit (1,864 non-test source files, 273,543 lines, seven parallel reviewers plus
mechanical clone detection).

This plan deliberately excludes everything owned by
[`work/plugin-api-boundaries`](./npm-package-boundaries.md), which has 35 commits
and 301 changed files in flight migrating entity packages onto the declarative
`defineEntity` surface. Overlap was checked file by file before scoping; see
"Explicitly out of scope" below.

## Goal

Every duplicated contract in this repo is one of two things: a copy that exists
for a real boundary reason and is _guarded_, or a copy that should not exist.
Today the repo has both kinds, plus two live defects caused by the unguarded
ones. This plan closes the defects and converts the necessary copies into
guarded ones.

## Current baseline

The repo is in better shape than a duplication audit usually finds:

- Exact-clone density is 1.18% across the main tree, 1.06% across `entities/`.
- Zero deep imports into any package's `src`/`dist`; zero cross-package relative
  imports outside test fixtures. `bun run arch:check` passes over 3,012 modules.
- The largest clone cluster — ~335 lines of deploy scripts identical in three
  places — is **already the pattern this plan generalizes**: generated by
  `copyDeployScripts` at build time, guarded by a drift test in each consuming
  package, documented at `shared/deploy-support/src/index.ts:88-98`.

The problems are structural, not textual, and a clone detector cannot see them.

## Problems to solve

### 1. A duplicated schema silently drops configured site identity

`siteMetadataSchema` exists three times. The copy backing site config and job
payloads (`plugins/site-builder/src/types/site-metadata-schema.ts:22-35`) omits
`represents`. Measured:

```
user configures represents: "brain"
  via site-builder config/job path -> undefined
  via canonical message-bus path   -> brain
```

`plugins/site-builder/src/lib/build-site-layout-info.ts:16` then falls back to
`"anchor"`, so a site configured as a brain renders as an anchor.

The copy is annotated `z.ZodType<SiteMetadata, SiteMetadata>` — an annotation
that is supposed to guarantee conformance and does not. This is the concrete
proof that the repo's dominant zod idiom provides no drift protection.

### 2. Seven of nine ATProto record schemas accept arbitrary fields

`buildAtprotoRecordSchema` (`shared/atproto-contracts/src/record-schemas.ts:196-208`)
applies `.passthrough()` to every lexicon, then bolts strictness onto exactly one
record (`ai.rizom.brain.card`) via `refineBrainCardRecord` — a hardcoded field
list that duplicates the lexicon JSON it was built from.

Verified by constructing a minimal valid record per lexicon and adding a junk
field: 7 of 9 accept **and retain** it. Adding a property to the card lexicon
without editing the hardcoded list makes valid records fail validation.

### 3. Published SDK types are hand-maintained copies with no guard

Two instances where a copy is genuinely required at a publish boundary — the
published packages may not import private `@brains/*` (enforced for declarations
by `findInternalDeclarationImports`) — but nothing keeps the copy honest.

- **`ServicePluginContext` / `EntityPluginContext` declared twice** in one
  package: `shell/plugins/src/public/types.ts:490,499` versus
  `service/context.ts:92` / `entity/context.ts:77`. The `public/` copies flow
  through `public/plugin-api.ts` → `@brains/plugins/public/plugin-api` →
  `packages/brain-cli/src/entries/plugins.ts` → published `@rizom/brain/plugins`.
  The SDK copy of `EntityPluginContext` is missing `entityService`, `ai`, and
  `permissions` — three members the runtime object actually has, invisible to
  external plugin authors.
- **54 lines of recursive JSON conditional types copied verbatim**:
  `packages/site/src/index.ts:10-63` ≡ `shared/contracts/src/json.ts:1-55`,
  including the 32-level depth cap and identical doc comments. `@brains/contracts`
  has `test/json.test.ts`; the published copy has none. Five independent
  declarations of this family exist repo-wide.

### 4. Dead weight that makes the inventory lie

- Nine directories match a workspace glob but have no `package.json` — leftovers
  from deleted packages, all untracked, all still globbed by turbo:
  `plugins/{email-resend,email-triage,rover-onboarding,sveltia-cms}`,
  `shared/{email-contracts,theme-signal}`, `sites/{rizom-foundation,rizom-work}`,
  `interfaces/discord`.
- `plugins/email-workflows/src/reply-drafts/` — 952 lines imported by nothing
  outside its own tests. No `index.ts` export, no `plugin.ts` registration, no
  CMS workspace. It also carries duplicate copies of three cluster schemas, so it
  multiplies the cost of every change made elsewhere in the email cluster.

## Phases

Each phase is a vertical slice: test first, then implementation, then the gates.
Every phase leaves the tree green and is independently revertable.

### Phase 1 — One site-metadata schema (fixes defect 1)

1. Add a failing test asserting `represents: "brain"` survives the site-builder
   config path and that the config schema's output equals the canonical schema's
   output for the same input.
2. Delete `plugins/site-builder/src/types/site-metadata-schema.ts` and
   `plugins/site-builder/src/lib/site-metadata.ts`'s local trio; import
   `siteMetadataSchema` / `siteMetadataCTASchema` / `siteMetadataSectionSchema`
   from `@brains/site-composition` (already a declared dependency).
3. Add `siteLayoutInfoSchema = siteMetadataSchema.extend({...})` in
   `shared/site-composition/src/metadata.ts`, replacing the 35-line restatement
   at `:108-143`. The TypeScript side already models this as
   `interface SiteLayoutInfo extends SiteMetadata`.

### Phase 2 — Lexicon-derived strictness (fixes defect 2)

1. Add a test asserting every canonical lexicon rejects an unknown top-level
   field, and that the card lexicon's nested `brain`/`anchor` objects reject one
   too — a table-driven test over `canonicalAtprotoRecordSchemas`, so new
   lexicons are covered automatically.
2. Have `buildAtprotoObjectShape` collect its own key set and emit `.strict()`
   uniformly; delete `refineBrainCardRecord`, `reportUnexpectedFields`, and the
   `lexicon.id === "ai.rizom.brain.card"` branch.
3. Verify the nine entity packages that publish records still round-trip.

### Phase 3 — Subtraction — **revised after checking provenance; nothing to do here**

The audit proposed deleting two things. Checking each before acting reversed both
calls:

1. **The nine stale directories are not in the repository.** They exist only as
   untracked `.turbo`/`dist` leftovers in a long-lived working copy; a clean
   checkout has none of them. There is no commit to make. The cleanup is a local
   `rm -rf` in whichever working copy has accumulated them, not a change to the
   tree.
2. **`plugins/email-workflows/src/reply-drafts/` is live work, not dead code.**
   It was added 2026-08-15 (`f6d93c7aa feat(inbox): add source-backed reply
drafting`) and last touched 2026-08-17 (`c5bf4cfbf feat(operator): complete
inbox semantic integration`), which is the current head of the active
   `feat/public-operator-universal-semantics` worktree.

The reviewer's observation was accurate as far as static analysis goes — the
subtree really has no export, no registration, and no CMS workspace. The
inference drawn from it was wrong. "Nothing imports it" distinguishes abandoned
code from half-landed code only if you also look at when it was written; here it
is a feature three days old with its wiring still in flight. Deleting it would
have destroyed someone's in-progress work.

Whoever finishes that feature owns the duplicate schemas it carries
(`draftSourceAddressSchema`, the third `abortSignalSchema`, the
`source-unavailable` outcome variant); they should collapse onto the shared ones
as part of landing it, not have them deleted underneath.

### Phase 4 — Guard the published copies (fixes defect 3)

1. **Context types.** Delete the shadow `ServicePluginContext` /
   `EntityPluginContext` declarations in `shell/plugins/src/public/types.ts` and
   re-export the real ones from `service/context.ts` / `entity/context.ts`. If a
   declaration-leak gate rejects that, fall back to a drift test asserting the
   two shapes are mutually assignable — but re-export first, because the copies
   exist by accident, not by constraint.
2. **JSON types.** Keep the `packages/site` copy (the published SDK genuinely
   cannot import `@brains/contracts`) and add the guard the deploy scripts
   already demonstrate: a test asserting the two modules' source text matches,
   plus a header comment naming the canonical source. Extend
   `shared/contracts/test/json.test.ts` coverage to the published copy.

## Explicitly out of scope

Owned by `work/plugin-api-boundaries`; touching any of it guarantees conflicts:

- All of `entities/` — 301 files in flight there. This includes the portfolio
  publish-payload defect found in the audit (portfolio sends
  `{entityType, entityId, publishedAt}` where the contract requires
  `result: {id, url?}`): that branch deletes the hand-rolled publish handler
  entirely in favour of declarative publish participation, fixing it by
  construction. **Do not fix it here.**
- `shell/plugins/src/entity/**`, `public/entity-definition.ts`,
  `service-definition-contract.ts`, and the declarative plugin bases.
- The entity publish pipeline, atproto projection registration, entity
  datasources and list formatters.

## Deferred, with reason

The bulk migration of the remaining **419 hand-written types that shadow their
own zod schema** (Style A → the `z.output` idiom) is not in this plan.

It is the largest single finding in the audit and it is mechanical, but:

- `work/plugin-api-boundaries` is already doing it inside `entities/`
  (126 → 113) as a side-effect of the declarative migration, and has 301 files
  open across `shell/` — a wide mechanical sweep now would conflict with almost
  all of it.
- The idiom is settled and documented by that branch's own reasoning: `z.output`
  produces a type _alias_, which carries the implicit index signature `JsonObject`
  requires; a hand-written `interface` does not. Deriving is what keeps rendered
  shapes renderable, not a style preference.

This plan lands the _guards_ that stop published contracts from drifting. The
sweep should follow once `plugin-api-boundaries` merges, scoped per package
group, and is worth its own plan.

## Validation

Per phase: `bun test` for the touched packages. Before finishing:
`bun run typecheck`, `bun scripts/lint.mjs --force --filter <touched>`,
`bun run arch:check`, and a changeset per affected package group.
