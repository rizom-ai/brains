# Onboarding emails

## Status

Planned. Copy is drafted in [../onboarding-email-mockups.html](../onboarding-email-mockups.html) and awaits review before Phase 1.

## Current state

A brain sends two onboarding emails, written in three places, all plain text:

| Email                       | Recipient                                       | Source                                                                       |
| --------------------------- | ----------------------------------------------- | ---------------------------------------------------------------------------- |
| Setup email, default copy   | Anchor of a `brain init` brain                  | `resolveSetupEmail` in `shell/auth-service/src/auth-service-plugin.ts`       |
| Setup email, Rover override | Anchor of a brains-ops provisioned brain        | `createSetupEmailConfig` in `packages/brains-ops/src/default-user-runner.ts` |
| Invitation                  | Person invited to an existing brain by an Admin | `InvitationChannels.send` in `shell/auth-service/src/invitation-channels.ts` |

Defects shared across them:

- Expiry is printed as an ISO timestamp (`2026-10-06T14:00:00.000Z`).
- No HTML part, although `ChannelDeliveryInput.html` and `NOTIFICATIONS_SEND` already carry one end to end.
- The invitation names neither the brain nor the inviter: subject `Join <hostname>`, body "You have been invited to access this brain."
- The default setup email leads with a raw setup link and an MCP endpoint, and does not say what a passkey is or what to do after setup.
- The Rover override links to a markdown file on GitHub and hardcodes the product name in operator config.

## Decisions

### One renderer

`shell/auth-service/src/onboarding-emails.ts` exports `renderOnboardingEmail(input): { subject, text, html }`. The input is a Zod schema discriminated on `kind`:

- `anchor-setup` — `setupUrl`, `expiresAt`, `origin`.
- `invitation` — `setupUrl`, `expiresAt`, `origin`, `brainName`, `role` (`admin` | `trusted`), optional `inviterName`.

Both emails are rendered by this function only. The text and HTML parts come from the same copy, so they cannot drift apart.

### The `setupEmail` override is removed

`auth-service.setupEmail` becomes the recipient address only (`z.string().email()`). The `{ to, subject, body }` object form and `{{setupUrl}}` template interpolation are deleted.

- `brain init` already writes the string form; no change.
- The brains-ops runner emits `setupEmail: <address>`; `createSetupEmailConfig` is deleted.
- A brain.yaml that still carries the object form fails config validation at boot. Pilot brain.yaml files are regenerated by `brains-ops reconcile` against the release that contains this change, before that release is pinned.

### Names in the copy

- **Brain name**: `context.identity.getProfile().name`, using the existing "empty or `Unknown` means absent" rule from `resolveProfileDisplayName`. Fallback: the issuer hostname. `InvitationService` receives it through a new `getBrainName` option, read at send time.
- **Inviter**: `authInvitations.createdByUserId` → `authUsers.displayName`, looked up when the email is sent, so resends and recovered deliveries carry it too. When the creator no longer exists, the subject and body drop the inviter clause.
- **Role**: `admin` → "an admin"; `trusted` → "a trusted member", matching the `Trusted` label in Studio. The email makes no claims about permissions.
- **Product name**: the copy says "brain". Rover-specific wording goes away with the override, because the same renderer serves client and team brains.

### Expiry

Rendered as `Intl.DateTimeFormat("en-GB", { dateStyle: "full", timeStyle: "short", timeZone: "UTC" })` plus ` UTC`, e.g. "Tuesday 6 October 2026 at 14:00 UTC". The recipient's time zone is unknown, so UTC is stated explicitly.

### HTML

- Single column, max 560px, table layout with inline styles. No images, web fonts, or external CSS.
- One primary button for the setup link, with the raw URL repeated below it for clients that strip buttons.
- Every interpolated value is escaped with the existing `escapeHtml` from `pages.ts`, moved to a shared module inside auth-service.
- Neutral palette; no per-brain theming.

### Content

The anchor setup email says, in order: the brain at this address is ready; the setup button; what a passkey is (one sentence); a single-use and expiry line, plus "don't forward"; what happens next (signed in on the dashboard, chat at `/chat`, Studio at `/studio`); the MCP endpoint as a footer line for connecting other AI tools; and "didn't expect this? ignore it, the link expires on its own".

The invitation says: who invited you to which brain, at which address, and in which role; the setup button; what a passkey is; the single-use and expiry line; what happens next (chat and Studio); and the same "didn't expect this" footer.

The exact wording lives in the mockups and becomes the test fixtures.

### Out of scope

User-editable email copy (for example, emails as an entity type). The renderer's typed input is the seam such a change would replace.

## Phases

Each phase lands with its tests written first.

### Phase 1 — Invitation email

1. Tests: `onboarding-emails.test.ts` covers the invitation kind with and without an inviter, both roles, the expiry format, and HTML escaping of the brain and inviter names. `invitation-channels.test.ts` asserts that the provider receives `subject`, `text` and `html` from the renderer. `auth-invitation-service.test.ts` asserts that a resend carries the inviter name.
2. Implement the renderer (invitation kind), the inviter lookup in `InvitationService`, the `getBrainName` option wired from `AuthServicePlugin`, and the `escapeHtml` move.
3. Verify: start the team posture (`bun start:team` in `packages/brain-cli`), invite `smoke@rizom.ai` from Studio, and read the delivered message from the smoke mailbox in both an HTML and a text-only view.

### Phase 2 — Anchor setup email and override removal

1. Tests: renderer tests for `anchor-setup`. An `auth-service.test.ts` case asserts that the `NOTIFICATIONS_SEND` payload carries `html`. A config-schema test asserts that the object form of `setupEmail` is rejected. `reconcile.test.ts` asserts that the generated brain.yaml has `setupEmail: <address>`.
2. Implement: `resolveSetupEmail` delegates to the renderer; narrow the `setupEmail` schema; delete `createSetupEmailConfig`; update `operator-playbook.md` (setup verification step); add a changeset that marks the `setupEmail` narrowing as breaking.
3. Verify: start the personal posture (`bun start:personal`) on an empty auth store with `SETUP_EMAIL_TO=smoke@rizom.ai`, and read the delivered setup email from the smoke mailbox.
