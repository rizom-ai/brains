# Offline 0.2 → 0.3 database importer

**Under development; not yet a production migration/deploy command.** This
separate package is allowed to carry libSQL. The 0.3 application is not.

## Input

Use a verified 0.2 predeploy snapshot directory containing `manifest.json`,
`manifest.sha256`, and its captured database files. The importer validates the
manifest checksum, source version, file sizes and hashes, database integrity,
and foreign keys. It rejects symlinked files, database sidecars, missing files,
and processing jobs. Never pass an active data directory.

Stop all 0.2 writers first, including auth replica synchronization. Resolve any
in-flight jobs on 0.2 and recapture the backup; the importer deliberately refuses
to turn uncertain side effects into automatic retries. Pending jobs are preserved.
Keep the original snapshot and old binary for rollback.

```sh
# From this package, until a release artifact is published:
bun run build
bun dist/brain-db-migrate.js \
  --backup /srv/backups/verified-0.2-snapshot \
  --destination /srv/brain-0.3 \
  --source-stopped
```

The destination's parent must exist. The destination must not exist and must be
outside the backup. The importer never opens a source database handle: it copies
verified files into a private staging directory and operates only on those copies.

## Output and verification

Output layout:

- `brain.db`: entities, derived embeddings, search/projection state, job outbox
- `brain-jobs.db`: durable jobs
- `conversations.db`: conversations and messages
- `runtime-state.db`: runtime records
- `auth/auth.db`: accounts, passkeys, sessions, signing keys, encrypted settings
- `import-report.json`: source provenance, destination file hashes, and preserved
  table counts/content digests

The source database schemas are migrated using the destination release's bundled
migration files. Legacy FTS5 is removed from the staging copy using libSQL before
Turso opens it. Embeddings are derived and regenerated by the runtime provider;
the retired separate `embeddings.db` is not copied into the destination.

Every original durable table is compared by primary key, across its original
columns, after migration. Verification is paged rather than loading the corpus
into memory. Unsupported unkeyed tables or unexpected durable transformations
fail closed. A fresh Turso connection verifies the migrated state after the
migration connection has checkpointed and closed. Only then is staging renamed
to the final destination. There is no automatic engine fallback.

**This imports databases only.** It does not restore Git bundles/patches, copy
configuration, preserve environment secrets for you, or change deployment mounts.
Restore the content checkout and configuration separately, preserving the auth
account-settings encryption key. Point the runtime's database configuration and
`auth-service.storageDir` at the new paths. Complete startup, auth, job recovery,
search, and content smoke checks with traffic fenced before switching traffic.
The report intentionally says `databases-verified`, not deployment-ready.

## Failure and retry

Failures never publish the final directory. An incomplete staging directory is
retained for diagnosis; do not start the application against it. Normal failure
and cancellation release the destination's `.import-lock`, so retry creates a new
staging directory from the same unchanged backup.

A hard-killed importer can leave its lock. Confirm the old importer is gone before
manually removing that lock and retrying. Never delete a lock merely because a
deadline elapsed. Existing destinations are never overwritten.

Rollback before accepting writes uses the retained 0.2 binary and snapshot. After
0.3 accepts writes, restoring the old snapshot loses those new writes: agree the
recovery policy before opening traffic. Never open 0.3 files with the 0.2 engine.

## Remaining release gates

- Turso-aware operational backup and verified restore (including auth).
- Full content/configuration restore and deployment integration.
- Rehearsed interruption/rollback and auth/login/job execution on a representative
  production snapshot, then rover and real-instance soak.
